L03260 ## Global Prior-Art Landscape and Architectural Convergence
L03261 A comprehensive investigation into the global prior-art landscape for agent wallets reveals a rapidly maturing ecosystem moving toward a convergence on specific architectural patterns designed to balance the autonomy of AI with the security of financial assets [[13,34]]. Rather than a chaotic market of disparate solutions, a clear spectrum of approaches has emerged, each with distinct trade-offs between security, flexibility, and developer overhead. For a competition entry aiming to innovate, understanding these existing paradigms is crucial, as the most promising path forward often lies in combining proven infrastructure with novel applications rather than reinventing fundamental components from scratch [[5,23]]. The leading systems can be broadly categorized into four primary architectural models: custody-separated models, policy-enforced smart accounts, session key-based models, and human-verifying models.
L03262 The most advanced and secure architectural pattern is the **Custody-Separated Model**, exemplified by Coinbase's Agentic Wallets [[10,12]]. In this design, the AI agent's logic and decision-making process are completely decoupled from wallet custody. Private keys are never exposed to the agent's runtime environment; instead, they are stored within highly secure, isolated environments like Trusted Execution Environments (TEEs), such as AWS Nitro Enclaves [[10,12]]. When the agent determines a transaction is necessary, it sends an authorization request to the enclave, which performs the cryptographic signing operation internally and returns only the signed transaction data [[12]]. This architecture provides a "several orders of magnitude safer" alternative to older models where agents managed their own keys, a flaw that led to supply chain attacks and fund theft [[10,12]]. Platforms like Turnkey and Privy adopt similar principles, using MPC and policy engines to enforce guardrails at the signing layer, effectively creating a hardware-backed security boundary independent of the AI's reasoning [[13,34]]. This model represents the current industry gold standard for high-value autonomous operations, providing maximum protection against private key exfiltration and unauthorized signing [[12]].
L03263 A second, highly promising pattern is the **Policy-Enforced Smart Account**, built upon the foundation of Account Abstraction enabled by standards like ERC-4337 [[23,24]]. This approach leverages programmable smart contract wallets as a dynamic, on-chain gatekeeper for transactions initiated by an agent [[78]]. Instead of relying solely on off-chain policy checks, these wallets encode spending limits, allowlists, and other business rules directly into the smart contract's `validateUserOp` function [[23]]. Since these rules are enforced by the blockchain's consensus mechanism, they are immutable and cannot be bypassed by a compromised or malicious agent [[78]]. Projects like Gnosis Safe have integrated ERC-4337 modules, allowing them to act as sophisticated policy engines [[23]]. Other implementations include Kernel and Modular Accounts, which provide developers with flexible templates for creating these programmable wallets [[23]]. This architecture offers a powerful combination of flexibility and security, allowing developers to define complex, context-aware rules that are automatically enforced by the network itself. For a competition project, building on this pattern would demonstrate a deep understanding of modern wallet security and provide a robust, auditable foundation.
L03264 The **Session Key-Based Model** occupies a middle ground, granting the agent temporary, scoped permissions rather than permanent control [[45]]. Standards like ERC-7715 enable the creation of short-lived "valet keys" that can be used for a limited time or for a specific set of actions [[12,31]]. This reduces the blast radius of a compromised key. Coinbase's AgentKit was initially built on this model, but its open-source nature and lack of built-in guardrails made it vulnerable when developers failed to implement their own safety layers [[45]]. The subsequent launch of Coinbase's Agentic Wallet product demonstrates a more secure evolution of this pattern, using short-lived session keys that are enforced by a robust, off-chain policy engine controlling session caps, transaction limits, and KYT screening [[10]]. This layered approach—combining revocable permissions with centralized policy enforcement—is a practical and effective strategy for balancing autonomy with control.
L03265 Finally, the **Human-Verifying Model** prioritizes ultimate security over pure autonomy by requiring explicit human confirmation for every action. Solutions like MoonPay Agents, in partnership with Ledger, integrate a physical device into the workflow; every transaction proposed by the agent must be reviewed and cryptographically signed on a hardware wallet like a Ledger Nano [[12,43]]. This creates an extremely strong defense against remote attacks, as there is no way for a remote actor to sign a transaction without physical access to the device. While this model is exceptionally safe, it may conflict with the spirit of the competition's "autonomous" requirement if it implies zero human intervention for any action. However, it serves as an important benchmark for the highest level of security and could be adapted into a hybrid system where routine micro-transactions are fully automated, but larger payments require human-in-the-loop approval.
L03266 Beyond these core models, a rich ecosystem of tools and protocols has emerged to support agentic finance. The x402 protocol, revived by Coinbase and Cloudflare, provides a standardized way for agents to pay for services via HTTP, enabling a new economy of machine-to-machine commerce [[42,64]]. Stablecoins have become the de facto currency for these transactions due to their low cost, instant settlement, and permissionless nature, which avoids the need for traditional KYC [[42,43]]. L03279 To achieve a high score in the "Task Completion" and "Innovation" categories of the competition, a winning agent wallet must address a meaningful, real-world financial problem. L03280 One of the most significant and under-addressed areas is **SME Treasury and Cash-Flow Operations**. Small and medium-sized enterprises (SMEs) face immense challenges in managing their day-to-day financial operations. Finance teams spend an estimated 15-20 hours per month manually reconciling payments and preparing audit documentation, time that could be better spent on strategic analysis [[29]]. Furthermore, processing recurring bills, routing invoices through email approval chains, and executing scheduled cash sweeps introduce significant room for human error and consume considerable operational resources [[29]]. Cross-border payments are particularly problematic, taking 3-5 days to settle through traditional banking systems and incurring fees of 3-5% [[29]]. An autonomous agent wallet can directly address these issues by automating the entire payment lifecycle. It can monitor invoice dates, verify delivery of goods or services through integration with logistics oracles, and execute payments in stablecoins across borders in minutes for a fraction of the cost [[29]]. The blockchain provides an immutable, tamper-proof ledger of every transaction, which automatically generates verifiable documentation, streamlining compliance and accelerating month-end close from weeks to days [[29]]. This use case is ideal for the competition as it solves a massive, quantifiable business problem, demonstrating clear value beyond the crypto-native ecosystem.
L03281 Another high-potential domain is **Autonomous Procurement and Micropayments**. As software becomes increasingly modular and services are consumed on a pay-per-use basis, the volume of small-value transactions grows exponentially. This creates a "micropayment problem" where traditional payment rails are economically unfeasible due to high fixed costs (e.g., credit card processing fees of 2-3% plus a per-transaction fee) [[64]]. Simultaneously, managing subscriptions and invoicing for these services is administratively burdensome [[26]]. Autonomous agents, from GPU clusters renting compute power to data-scraping bots paying for API calls, require a seamless way to pay for resources without human intervention [[26,35]]. An agent wallet designed for this purpose would integrate with service discovery platforms like the x402 Bazaar, allowing an agent to discover payable APIs, evaluate them based on price and performance, and pay for each call in real-time using a stablecoin [[26,44]]. The economic model of blockchain-based micropayments, with costs measured in cents, makes this scalable [[29]]. This use case is highly innovative and aligns perfectly with the emerging "agentic economy," showcasing an application that is impossible with traditional finance infrastructure [[42,44]].
L03282 The insurance industry presents another area ripe for disruption through agentic AI. Claims handling is a major source of customer dissatisfaction, accounting for over 62% of all complaints in 2024 [[71]]. The process is notoriously slow and complex, often involving siloed data and manual workflows where customers must repeat information across multiple channels [[71]]. Fraud detection is resource-intensive, and resolving claims can take weeks or months [[29]]. An autonomous agent can orchestrate the entire claims lifecycle for a narrow class of eligible claims, such as minor car accidents. The agent could ingest claim data, including photos and accident reports, validate it against policy coverage dates using external data sources like weather APIs, score the claim for fraud probability using machine learning models, and either auto-settle eligible claims or route complex cases to a human adjuster with a complete, summarized case file [[69,70]]. This model, which relies on a strict "eligibility gate" to restrict touchless settlements to clear-cut cases, can reduce processing times by over 75% and cut costs by 30-40% [[70]]. The blockchain's immutable record provides a transparent audit trail for regulators and a single source of truth for the entire claim history, enhancing trust and compliance [[29]].

L03410 ## Advanced Security Architecture and Threat Modeling
L03411 For a solution to succeed in the 2026 Shenzhen International FinTech Competition, security is not merely a feature but a foundational pillar, carrying a 30% weight in the judging criteria [[2]]. The analysis of existing systems and academic literature reveals that autonomous agent wallets are subject to a unique and severe threat landscape, dominated by attacks that manipulate the agent's decision-making process rather than exploiting traditional cryptographic weaknesses [[7,49]]. The most critical vulnerability is prompt injection, ranked as the number one LLM vulnerability, which has been the root cause of over $45 million in losses linked to agent-related protocol flaws [[9,12]]. Therefore, a winning entry must be architected around a defense-in-depth strategy that creates multiple, independent layers of security, ensuring that the AI's reasoning process cannot be hijacked to compromise funds or data. This involves a clear separation of concerns between the AI's planning module, a trusted policy enforcement layer, and a protected signing environment.
L03412 The primary threat model for an autonomous agent wallet must account for several attack vectors. **Direct Prompt Injection** occurs when an attacker directly feeds malicious instructions to the agent, for example, by posting a comment on a social media page the agent monitors [[7]]. A real-world experiment demonstrated this vulnerability, where an attacker manipulated an ElizaOS bot into transferring 0.001 ETH by posting a malicious reply to a public thread [[7]]. **Indirect Prompt Injection** is an even more insidious variant, where the malicious payload is hidden within external content that the agent is trained to process, such as the HTML of a webpage, the metadata of a document, or the response from an API [[7,8]]. Zscaler identified campaigns where attackers poisoned search results and crafted fraudulent websites to trick agents into making unauthorized payments [[8]]. A more advanced threat is **Memory Poisoning**, where an attacker gains access to the agent's persistent, external memory store and injects false historical data or instructions [[7]]. This can cause the agent to act on fabricated past interactions, making the malicious behavior appear legitimate and bypassing safeguards that rely on consistent intent over time [[7]]. Other significant threats include unauthorized modification of transaction details (recipient, amount, chain), replay attacks using previously signed messages, MEV-based griefing or front-running, and supply chain attacks where dependencies like libraries or data sources are compromised [[5,49,58]].
L03413 To counter these threats, the architecture must be deliberately designed to prevent the AI from having unchecked authority. The principle of "never give the LLM the keys" is paramount [[12]]. A robust, defense-in-depth security architecture should be composed of several distinct, logically separated layers:
L03414 1.  **AI Planning and Intent Layer:** This is the LLM's domain. Its responsibility is to analyze a high-level goal (e.g., "pay the monthly invoice"), break it down into a sequence of steps, and formulate a transactional intent. It should have no direct access to signing keys, private data, or the ability to construct and broadcast transactions on its own. Its output is a structured intent object, not a raw transaction [[5]].
L03415 2.  **Trusted Policy Enforcement Layer:** This is the most critical security boundary. Before any action is taken, the proposed intent from the AI must be passed to a policy engine for evaluation [[30]]. This engine should be implemented as independently as possible from the AI's runtime environment. For maximum security, this layer should be an on-chain smart contract, such as the `EntryPoint` contract in an ERC-4337 architecture [[23]]. The policy logic, written in the contract's code, can enforce immutable rules like spending limits (per transaction, daily cap, session limit), allowlists of approved addresses and contracts, and restrictions on transaction types [[32,78]]. This ensures that even if the AI is compromised and tries to request a malicious transaction, the on-chain check will reject it automatically. An off-chain policy engine can serve as a faster, more flexible preliminary filter but should not be the sole line of defense [[78]].
L03416 3.  **Transaction Simulation and Validation Layer:** Before a transaction is ever sent to a signing environment, it must be simulated on a local, forked node of the target blockchain (e.g., using Tenderly [[5]]). This step verifies that the transaction will have the intended effect and does not lead to unexpected state changes or revert. This protects against errors in the agent's logic or interactions with malicious contracts. The simulation should also validate that the proposed transaction complies with the rules checked by the policy engine.
L03417 4.  **Protected Signing Environment:** If keys are not fully segregated in a TEE, they must be managed securely. The MPC (Multi-Party Computation) model, where key shares are held by multiple parties (e.g., the user and a service provider), is a strong option [[10]]. The signing process should occur within a secure enclave (like a TEE) or an HSM (Hardware Security Module) to protect the keys from extraction [[12]]. The agent should only be able to request a signature for a transaction that has already been validated by the previous two layers.
L03418 5.  **Immutable Audit and Recovery Layer:** Every step of the process—from the original user intent, through the AI's plan, the policy check results, the simulation output, to the final signed transaction hash—must be recorded in a tamper-evident log [[37]]. This log should be stored immutably, ideally on-chain where possible, to provide a complete and auditable trail for debugging, dispute resolution, and compliance. This layer also includes emergency stop mechanisms, such as a time-locked function to pause the agent or revoke its permissions entirely, and clear procedures for recovering funds in the event of a compromise [[49]].
L03419 This layered architecture directly addresses the primary threats. Because the AI's only output is a structured intent object, it cannot directly command a fund transfer. The policy engine acts as an infallible gatekeeper, enforcing rules that are independent of the AI's compromised state. The simulation layer prevents logical errors, and the protected signing environment ensures keys are never exposed. Even if the AI's planning process is hijacked, the transaction it proposes will be rejected by the policy engine if it violates any rule.
L03420 Regarding formal verification, while it is a powerful technique for mathematically proving the correctness of smart contract code against a specification, its role in this project is limited [[16]]. It can be used to provide high assurance that the on-chain policy enforcement contract is free of bugs, which is a valuable practice. However, formal verification cannot prove that the AI's *intent* is correct or that its high-level goals are safe. It can only prove that the code behaves as written [[17]]. Relying on it for the agent's decision-making logic is impractical for a student team due to the high cost, time investment, and specialized expertise required [[16]]. Therefore, the focus should be on rigorous testing, including adversarial testing, and building a robust, layered architecture. Adversarial tests should be designed to systematically probe for vulnerabilities, such as crafting prompts to bypass filters, feeding the agent malicious data to poison its memory, and attempting to manipulate transaction parameters before signing [[49]]. The goal is to create a system that is not only secure by design but also fails safely, meaning that in the event of a failure, it defaults to a secure, locked-down state rather than continuing to operate in an unpredictable manner.
